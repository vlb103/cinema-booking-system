# API-GATE

Рішення щодо готовності контракту REST API до реалізації для інформаційної системи Cinema Booking System (версія 1.0.0).

Дата фіксації: 2026-11-03  
Рішення: **GO**  
Ухвалив: автор проєкту (vlb103)  
Артефакти: `docs/api/openapi.yaml`, `docs/api/api-model.md`, `docs/api/scenarios.md`, `spec/addendum-api.md`, `tests/contract/check_mock.py`, матриця простежуваності (Додаток А в `spec/srs.md`)

## Перевірка критеріїв

| № | Критерій | Результат | Підтвердження |
| :-- | :--- | :-- | :--- |
| 1 | Кожна суттєва API operation має обґрунтований зв'язок з REQ-ID | Виконано | 15 з 15 операцій мають `x-req-id`, усі REQ-F-001…REQ-F-020 покрито |
| 2 | Ресурси та термінологія відповідають предметній області та глосарію | Виконано | Ресурси User, Film, Hall, Session, Seat, Booking відповідають термінам глосарію SRS §1.3 |
| 3 | URI та HTTP-методи використовуються послідовно | Виконано | Іменники в множині, адміністративні операції під `/admin`, GET для читання, POST для створення, PATCH для часткової зміни, POST `…/cancel` для зміни статусу без видалення |
| 4 | Для операцій визначені request і response schemas | Виконано | Усі POST і PATCH мають схему тіла, крім скасування бронювання, якому тіло не потрібне. Усі відповіді мають схему |
| 5 | Визначені необхідні коди стану HTTP та єдина модель помилок | Виконано | Модель `Error` з 12 кодами, відповіді 400, 401, 403, 404, 409, 500 |
| 6 | Передбачені позитивні й негативні сценарії | Виконано | 18 позитивних і 33 негативні сценарії, покрито BDD-сценарії 1–6 і граничні випадки REQ-TDD-003 |
| 7 | API не розкриває без необхідності деталі внутрішньої реалізації | Виконано | Пароль лише в запитах реєстрації і входу, у відповідях його немає. Помилки не містять технічних деталей, лише `code`, `message`, `details` |
| 8 | OpenAPI specification проходить автоматичну валідацію | Виконано | Redocly CLI 1.25.0, 0 помилок, 3 попередження з обґрунтуванням нижче |
| 9 | Mock API запускається на основі затверджуваної специфікації | Виконано | Prism 5.12.0 у Docker за `openapi.yaml`, серверного коду немає |
| 10 | Основні позитивні й негативні сценарії відтворюються через mock API | Виконано | `check_mock.py` 51 з 51. Для 19 сценаріїв, що залежать від стану, відповідь запитується заголовком `Prefer` |

## Нова поведінка

Уся поведінка API, якої немає в SRS, оформлена в `spec/addendum-api.md` (ADD-01…ADD-13) і погоджена автором. Група відкладених пунктів (вихід, видалення, пагінація, журнали аудиту та інші) в API версії 1 не входить.

## Що переходить у реалізацію

На mock неможливо перевірити поведінку зі станом. Її перевіряють тести в реалізації за TDD.
1. Паралельні запити на одне місце, рівно 1 успіх (REQ-F-009, REQ-NF-006).
2. «Все або нічого» при зайнятому місці (REQ-F-010, REQ-NF-001).
3. Звільнення місць після скасування (REQ-F-013).
4. Повторне скасування без змін стану (REQ-F-014).
5. Новий сеанс з'являється в афіші (REQ-F-015).
6. Каскадне скасування бронювань сеансу (REQ-F-019).
7. Ігнорування поля `role` при реєстрації (REQ-NF-005).
8. Межа часу скасування в момент початку сеансу (REQ-F-012).

## Наслідки рішення

Контракт `docs/api/openapi.yaml` затверджено як основу для реалізації. Зміни контракту після API-GATE вносяться лише через доповнення до SRS і повторне проведення API-GATE.
