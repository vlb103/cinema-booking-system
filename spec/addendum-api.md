# Доповнення до SRS. Уточнення, прийняті при проєктуванні REST API

Документ доповнює `spec/srs.md` (версія 1.0.0) і сам SRS не змінює.
Джерела: `docs/api/api-requirements.md` (група 1 прогалин), `docs/api/api-model.md` (прийняті рішення 1–13), `docs/api/openapi.yaml`, `docs/api/scenarios.md`.

Кожен пункт уточнює вже наявну вимогу SRS і не додає нової функціональності. ID пунктів мають вигляд `ADD-NN`, у дужках номер рішення в `docs/api/api-model.md`.

## Таблиця 1 – Уточнення вимог SRS

| ID | Що уточнюємо | Вимога SRS | Як це видно в API | Сценарії |
| :--- | :--- | :--- | :--- | :--- |
| ADD-01 (1) | **Автентифікація запитів.** Після входу сервер видає токен доступу. Клієнт передає його в кожному захищеному запиті в заголовку `Authorization: Bearer <token>`. Афіша, схема залу, реєстрація і вхід токена не потребують | REQ-F-003, REQ-F-001, §3.3 («сесійний токен») | `POST /auth/login` повертає `LoginResponse` (`accessToken`, `tokenType: Bearer`, `user`). Схема безпеки `bearerAuth` діє глобально, для публічних операцій `security: []`. Без токена відповідь 401 `UNAUTHORIZED` | P-04, N-01–N-03, N-23 |
| ADD-02 (2) | **Ідентифікація місця.** Місце завжди передається парою «ряд + номер», нумерація з 1. Номери на зразок [5, 6, 7] у BDD-сценарії 2 означають місця одного ряду | Глосарій §1.3 «Місце», REQ-F-007, §5.3 сценарій 2 | Схема `Seat {row, number}` у `CreateBookingRequest.seats` і `Booking.seats`, `SeatState {row, number, status}` у схемі залу | P-05, P-06, N-09 |
| ADD-03 (3) | **Коди і формат помилок.** Усі помилки повертаються в одній моделі `Error` (`code`, `message`, `details[]`). Коди стану: 400 для валідації, 401 для автентифікації, 403 для прав, 404 для неіснуючого ресурсу, 409 для конфлікту стану, 500 для системної помилки | §3.3, критерії REQ-F-003, REQ-F-005, REQ-F-006, REQ-F-007, REQ-F-009, REQ-F-012, REQ-F-017, REQ-F-018 | `components/schemas/Error` з переліком 12 значень `code`. | ADD-05 (5) | **Правила реєстрації.** Email має коректний формат і не довший за 254 символи. Пароль від 8 до 128 символів, інших вимог немає. Email унікальний. Реєстрація не виконує вхід автоматично. Поле `role` у запиті ігнорується, роль завжди USER | REQ-F-003, REQ-F-004, REQ-NF-005, §3.1 п.2 | `POST /auth/register` зі схемою `RegisterRequest` (`format: email`, `minLength: 8`). Відповідь 201 `User` з `role: USER`. Некоректні дані дають 400 `VALIDATION_ERROR`, зайнятий email дає 409 `EMAIL_ALREADY_EXISTS` | P-03, N-18–N-21 |
| ADD-06 (6) | **Бронювання на недоступний сеанс.** Бронювати місця на скасований сеанс або на сеанс, що вже розпочався, заборонено | REQ-F-008, REQ-F-018 | `POST /bookings` дає 409 `SESSION_NOT_AVAILABLE`, для неіснуючого сеансу 404 `NOT_FOUND` | N-10, N-11 |

## Відкладено на потім

Нижче пункти, які в API версії 1 не реалізовано. Їх можна внести окремим доповненням до SRS пізніше.

1. Вихід із системи (logout).
2. Отримання одного бронювання за ID.
3. Фільтри афіші (за датою, фільмом) і перегляд одного фільму чи сеансу.
4. Видалення фільмів, залів і сеансів.
5. Редагування залу (суперечність між матрицею RBAC §2.2 і §3.2 п.2).
6. Ознака наявності активних бронювань і перегляд бронювань сеансу для адміністратора.
7. Пагінація списків.
8. Перегляд журналів аудиту адміністратором. Є лише рядок у матриці RBAC §2.2, функціональної вимоги немає, кандидат на нову вимогу.
