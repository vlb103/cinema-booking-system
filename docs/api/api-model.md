# Модель ресурсів і операції REST API (Cinema Booking System, v1)

Джерела: `spec/srs.md` (1.0.0), `docs/api/api-requirements.md`. Специфікація OpenAPI 3.0: `docs/api/openapi.yaml`.

Базовий URL `/api/v1`. Формат JSON. Час ISO-8601 UTC. ID числові.

## Ресурси

Назви ресурсів узято з глосарію SRS (§1.3).

| Термін SRS | Ресурс API | Шлях | Опис |
| :--- | :--- | :--- | :--- |
| Користувач | User | `/auth/*` | Обліковий запис, роль USER або ADMIN, внутрішній числовий ID |
| Фільм | Film | `/admin/films` (у публічній афіші вкладений у сеанс) | Назва, тривалість, опис |
| Зал | Hall | `/admin/halls` | Назва, прямокутна схема рядів і місць, місткість |
| Сеанс | Session | `/sessions`, `/admin/sessions` | Фільм у залі з часом початку, статус ACTIVE / CANCELLED |
| Місце | Seat | `/sessions/{sessionId}/seats` | Пара «ряд + номер», стан FREE / TAKEN на конкретному сеансі |
| Бронювання | Booking | `/bookings` | 1–6 місць користувача на сеанс, статус ACTIVE / CANCELLED |

Адміністративні операції зібрано під префіксом `/admin` (окремий розділ за REQ-F-006).

## Схеми даних

**User**: `id` (генерує сервер, не змінюється), `email`, `role` (USER, ADMIN).

**Film**: `id`, `title` (обов'язкова), `durationMinutes` (обов'язкова, ≥ 1), `description` (необов'язковий).

**Hall**: `id`, `name`, `rowsCount` (≥ 1), `seatsPerRow` (≥ 1), `capacity` (рахує сервер, `rowsCount * seatsPerRow`).

**Session**: `id`, `filmId`, `hallId`, `startTime`, `status` (ACTIVE, CANCELLED), `cancellationReason` (null для активного сеансу).
В афіші сеанс повертається як `SessionListItem` з вкладеними `film` і `hall` (id, name).

**Seat**: `row`, `number`. У схемі залу `SeatState` додає `status` (FREE, TAKEN).
**SeatMap**: `sessionId`, `sessionStatus`, `hall`, `seats[]`.

**Booking**: `id`, `userId`, `status` (ACTIVE, CANCELLED), `seats[]` (1–6), `session` (`SessionSummary`: id, startTime, status, filmTitle, hallName), `createdAt`, `cancelledAt`, `cancellationReason`.
`cancellationReason` заповнений лише тоді, коли бронювання скасовано разом із сеансом (REQ-F-020).

**Error** (єдина модель для всіх помилок):

```json
{ "code": "SEATS_TAKEN", "message": "Одне або кілька місць уже зайняті, бронювання не створено", "details": ["ряд 1, місце 3"] }
```

| code | HTTP | Коли |
| :--- | :--- | :--- |
| VALIDATION_ERROR | 400 | Некоректні дані: формат email, короткий пароль, 0 або понад 6 місць, повтор місця, місце поза схемою залу, порожня причина |
| UNAUTHORIZED | 401 | Немає токена або токен недійсний |
| INVALID_CREDENTIALS | 401 | Невірний email або пароль під час входу |
| FORBIDDEN | 403 | Немає прав за роллю або чуже бронювання |
| NOT_FOUND | 404 | Сеанс, бронювання, фільм або зал не існує |
| EMAIL_ALREADY_EXISTS | 409 | Email уже зареєстровано |
| SEATS_TAKEN | 409 | Хоч одне місце зайняте (у `details` перелік зайнятих) |
| SESSION_NOT_AVAILABLE | 409 | Бронювання на скасований або вже розпочатий сеанс |
| CANCELLATION_DEADLINE_PASSED | 409 | Скасування бронювання в момент початку сеансу або пізніше |
| SESSION_HAS_ACTIVE_BOOKINGS | 409 | Редагування сеансу з активними бронюваннями |
| SESSION_ALREADY_CANCELLED | 409 | Редагування або повторне скасування скасованого сеансу |
| INTERNAL_ERROR | 500 | Системна помилка (спільна відповідь `InternalError`, є в усіх операціях) |

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | Отримання афіші | GET | `/sessions` | Публічно | REQ-F-001, REQ-F-015 | 200, 500 |
| 2 | Отримання схеми залу сеансу | GET | `/sessions/{sessionId}/seats` | Публічно | REQ-F-002, REQ-F-013 | 200, 404, 500 |
| 3 | Реєстрація | POST | `/auth/register` | Публічно | REQ-F-003, REQ-F-004, REQ-NF-005 | 201, 400, 409, 500 |
| 4 | Вхід | POST | `/auth/login` | Публічно | REQ-F-003 | 200, 400, 401, 500 |
| 5 | Створення бронювання | POST | `/bookings` | USER | REQ-F-008, REQ-F-003, REQ-F-004, REQ-F-007, REQ-F-009, REQ-F-010, REQ-NF-001, REQ-NF-006 | 201, 400, 401, 403, 404, 409, 500 |
| 6 | Перегляд власних бронювань | GET | `/bookings` | USER | REQ-F-020, REQ-F-003, REQ-F-005, REQ-F-019, REQ-NF-004 | 200, 401, 403, 500 |
| 7 | Скасування бронювання | POST | `/bookings/{bookingId}/cancel` | USER (власник) | REQ-F-011, REQ-F-003, REQ-F-005, REQ-F-012, REQ-F-013, REQ-F-014, REQ-NF-004 | 200, 401, 403, 404, 409, 500 |
| 8 | Перегляд переліку фільмів | GET | `/admin/films` | ADMIN | REQ-F-015, REQ-F-006, REQ-NF-003 | 200, 401, 403, 500 |
| 9 | Додавання фільму | POST | `/admin/films` | ADMIN | REQ-F-015, REQ-F-006, REQ-NF-003 | 201, 400, 401, 403, 500 |
| 10 | Редагування фільму | PATCH | `/admin/films/{filmId}` | ADMIN | REQ-F-015, REQ-F-006, REQ-NF-003 | 200, 400, 401, 403, 404, 500 |
| 11 | Створення залу | POST | `/admin/halls` | ADMIN | REQ-F-015, REQ-F-006, REQ-NF-003 | 201, 400, 401, 403, 500 |
| 12 | Перегляд параметрів залів | GET | `/admin/halls` | ADMIN | REQ-F-015, REQ-F-006, REQ-NF-003 | 200, 401, 403, 500 |
| 13 | Створення сеансу | POST | `/admin/sessions` | ADMIN | REQ-F-015, REQ-F-006, REQ-NF-003 | 201, 400, 401, 403, 404, 500 |
| 14 | Редагування сеансу | PATCH | `/admin/sessions/{sessionId}` | ADMIN | REQ-F-016, REQ-F-006, REQ-F-017, REQ-NF-003 | 200, 400, 401, 403, 404, 409, 500 |
| 15 | Скасування сеансу | POST | `/admin/sessions/{sessionId}/cancel` | ADMIN | REQ-F-018, REQ-F-006, REQ-F-019, REQ-NF-003 | 200, 400, 401, 403, 404, 409, 500 |

Покриття. Кожна з REQ-F-001 … REQ-F-020 присутня хоча б в одному `x-req-id` (перевірено скриптом).

Чому скасування зроблено через `POST …/cancel`, а не `DELETE`. Бронювання і сеанс після скасування не видаляються, лише змінюють статус і залишаються в історії (REQ-F-013, REQ-F-019). Повторний виклик скасування бронювання повертає 200 з тим самим станом (REQ-F-014).

## Прийняті рішення по групі 1 прогалин

Рішення автора:
1. **Автентифікація**. `POST /auth/login` видає `accessToken`. У кожному захищеному запиті він передається в заголовку `Authorization: Bearer <token>`. Публічні операції (афіша, схема залу, реєстрація, вхід) токена не потребують.
2. **Місце**. Передається як пара `{ "row": 1, "number": 3 }`, нумерація з 1.

Прийняті найпростіші варіанти:

3. **Коди і формат помилок**. Одна модель `Error` (`code`, `message`, `details[]`) з таблицею кодів вище. Відповіді 400 для валідації, 401 для автентифікації, 403 для прав, 404 для неіснуючих ресурсів, 409 для конфліктів стану.
4. **Чуже бронювання** повертає 403, а не 404, як написано в REQ-F-005.
5. **Правила реєстрації**. Email у коректному форматі, до 254 символів. Пароль від 8 до 128 символів, інших вимог немає. Email унікальний, повтор повертає 409 `EMAIL_ALREADY_EXISTS`. Реєстрація не входить автоматично, після неї потрібен вхід. Поле `role` у тілі ігнорується.
6. **Бронювання на скасований або вже розпочатий сеанс** заборонене, повертає 409 `SESSION_NOT_AVAILABLE`.
7. **Склад полів сутностей**. Поля, як описано в розділі «Схеми даних». Схема залу прямокутна (`rowsCount` × `seatsPerRow`), без проходів і різних типів місць. Тривалість сеансу дорівнює тривалості фільму, окремого поля кінця немає.
8. **Перетин сеансів в одному залі** у v1 не перевіряється.
9. **Валідація місць у бронюванні**. Від 1 до 6 різних місць, кожне має існувати в схемі залу, інакше 400.
10. **Роль ADMIN** не може створювати бронювання і переглядати `/bookings`, обидва випадки повертають 403 (матриця RBAC §2.2, «Заборонено / не застосовується у v1»).
11. **Скасування сеансу**. Дозволене незалежно від наявності бронювань. Порожня причина або причина лише з пробілів повертає 400. Повторне скасування повертає 409 `SESSION_ALREADY_CANCELLED`. Скасований сеанс не можна редагувати. Відповідь містить кількість каскадно скасованих бронювань.
12. **Афіша** повертає сеанси зі статусом ACTIVE, які ще не почалися. Схема залу повертається для будь-якого наявного сеансу разом із `sessionStatus`.
13. **Редагування** фільму і сеансу через `PATCH`, змінюються лише передані поля, порожнє тіло повертає 400.

## Не включено у v1

- Уся група 2 прогалин з `docs/api/api-requirements.md` (вихід, одне бронювання за ID, фільтри афіші, видалення, редагування залу, ознака бронювань для адміністратора, пагінація).
- Перегляд журналів аудиту.
