# Функціональні вимоги та REST API (Cinema Booking System)

Джерело: `spec/srs.md` (версія 1.0.0). URI і HTTP-методи на цьому етапі не визначаються.

Типи:
- **Операція** — окремий виклик API, який ініціює клієнт;
- **Правило** — перевірка або поведінка всередині іншої операції (окремого виклику немає);
- **Не стосується API** — вимога реалізується лише в браузері чи інфраструктурі.

## Чого бракує в SRS для проєктування API

Нижче те, що потрібно для контракту API, але в SRS не описано або описано суперечливо. У таблиці вище цього не додано. Прогалини розділено на дві групи.

### Група 1 – Без цього контракт API не написати

1.1. **Спосіб автентифікації запитів**. SRS згадує «сесійний токен» і JWT (§6.2), але не визначає, що саме видається при вході і як передається в запитах.
1.2. **Ідентифікація місця в запиті**. Глосарій визначає місце парою «ряд + номер», а BDD-сценарій 2 використовує просто номери [5, 6, 7]. Не узгоджено.
1.3. **Коди відповідей і формат помилок**. SRS називає лише Forbidden, відмову в авторизації і конфлікт. Не визначено відповідь для помилки валідації (0 або 7 місць, порожня причина), для скасування після початку сеансу, для неіснуючого сеансу чи бронювання, а також єдиний формат тіла помилки.
1.4. **Правила реєстрації**. Вимоги до пароля і поведінка при вже зайнятому email не описані.
1.5. **Бронювання на скасований або вже розпочатий сеанс**. Заборона прямо не сформульована.
1.6. **Склад полів сутностей**. Фільм (назва, тривалість, опис лише з глосарію), зал (як задається схема рядів і місць), сеанс (чи є тривалість, кінець) не мають визначеного формату. Не описана перевірка перетину сеансів в одному залі. *Цього пункту не було в жодній із названих груп. Віднесено до групи 1, бо без полів неможливо описати тіла запитів і відповідей. Потрібне рішення автора.*

### Група 2 – Можна винести в доповнення до SRS або відкласти

2.1. **Вихід із системи (logout)**. Операції немає.
2.2. **Отримання одного бронювання за ID**. Критерій REQ-F-005 говорить про «перегляд чужого бронювання», але описано лише список у кабінеті.
2.3. **Фільтри афіші та перегляд одного фільму чи сеансу**. Фільтрація за датою чи фільмом не описана. Не визначено, що означає «актуальні» сеанси (лише майбутні? чи показувати скасовані?).
2.4. **Видалення фільмів, залів і сеансів**. Не передбачено ніде.
2.5. **Редагування залу**. У матриці RBAC (§2.2) є «додавання / редагування фільмів і залів», а в §3.2 п.2 лише «створення та перегляд». Суперечність.
2.6. **Ознака наявності активних бронювань для адміністратора**. §3.2 п.4 блокує поля редагування сеансу при бронюваннях, але не описано, як адмін-клієнт про це дізнається. Перегляд бронювань сеансу адміністратором теж не передбачено.
2.7. **Пагінація списків** (афіша, бронювання). Не згадується.
2.8. **Перегляд журналів аудиту**. Є лише в матриці RBAC, без функціональної вимоги, фільтрів і формату відповіді. У першу версію API не входить, це кандидат на доповнення до SRS.
